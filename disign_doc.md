# Сервис оценки стоимости квартиры

## 1. Задача и контекст

Сервис даёт покупателю или продавцу ориентир для сравнения цен квартир. Входные характеристики – площадь, число комнат, этаж и этажность дома. Результат – полная цена в рублях.

Постоянная оценка не учитывает различия между квартирами. Модель должна использовать зависимости в данных и давать меньшую ошибку, чем простое базовое решение. Если улучшения нет, усложнение сервиса не оправдано.

### Текущее состояние и ограничения

- Работают веб-форма и Flask API. Вместо обученной модели используется заглушка: 10 млн рублей для любого корректного запроса.
- Данных и процесса обучения в репозитории пока нет. Качество оценки неизвестно.
- Проверка входных данных частичная. Без поля площади сервер возвращает 500. Неверная площадь обрабатывается с HTTP 200. Формат ошибок неоднороден.
- После заполнения полей формы их названия не видны: постоянных подписей нет.

## 2. Цели и границы

- Давать оценку цены по характеристикам квартиры.
- Обеспечить воспроизводимое обучение и сравнение моделей.
- Связать версии кода, данных и модели.
- Контролировать работу сервиса и замечать изменения входных данных.

### Антицели

- Обслуживание высокой нагрузки.
- Сложная облачная инфраструктура.
- Использование фотографий и текстов объявлений как признаков.
- Замена профессиональной оценки недвижимости для заключения сделки.

## 3. Данные и критерии успеха

Для обучения нужен табличный набор с входными характеристиками и ценой квартиры. Источник, город и период данных не определены. Данные объявлений позволяют оценивать цену предложения; цена сделки из них неизвестна.

Местоположение пока не входит в признаки. Это ограничивает точность оценки, особенно при сравнении разных районов. Необходимость географических признаков определяется после выбора данных.

Данные проверяются на пропуски, недопустимые значения и дубликаты. Повторные объявления одной квартиры исключаются из пересечения выборок. При наличии идентификаторов домов разделение учитывает группы; для прогноза будущих цен – временной порядок.

Тестовая выборка фиксируется до подбора модели и используется для итоговой оценки. Преобразования признаков обучаются только на обучающей части.

Варианты модели сравниваются на валидационной выборке или кросс-валидации внутри обучающей части.

Первая модель – линейная регрессия: простое решение, с которого удобно начать сравнение. Baseline – медиана цены обучающей выборки. Он отличается от текущей заглушки и ещё не реализован.

Основная метрика – MAE, средняя абсолютная ошибка в рублях. Дополнительная – MAPE, средняя абсолютная ошибка в процентах от цены. Для неё используются только положительные цены; ошибки дешёвых квартир сильнее влияют на результат. Метрики также оцениваются по группам площади и стоимости.

Критерии успеха:

- MAE модели ниже MAE медианного baseline на одной фиксированной тестовой выборке.
- Повторный запуск на тех же данных, с теми же параметрами и окружением воспроизводит результат.
- Сохранённая модель загружается в сервис и даёт тот же прогноз, что и при отдельном вызове на тех же признаках.

Это минимальные критерии работоспособности решения. Допустимая ошибка для пользователя требует отдельного согласования; преимущество над baseline само по себе не доказывает полезность оценки.

## 4. Проектное решение

Обучение включает подготовку данных, разделение выборки, формирование признаков, обучение, оценку и сохранение модели.

При предсказании форма передаёт параметры в API, сервис формирует признаки и вызывает модель. Сейчас четыре входных поля превращаются в семь признаков: площадь, этажность, три признака числа комнат и два признака первого или последнего этажа. Преобразования и порядок признаков при обучении и предсказании должны совпадать.

Форма доступна через `GET /`. Запрос цены – `POST /api/numbers` с токеном приложения. Текущий успешный ответ: `{"status": "success", "data": 10000000}`. Цена возвращается целым числом рублей.

Начальная конфигурация – локальный сервис и локальное хранение модели. Этого достаточно для проверки полного процесса без внешней инфраструктуры. Выбор модели уже поддерживается настройкой или аргументом запуска.

## 5. Развитие и открытые вопросы

Направления развития:

- DVC – версии данных и восстановление набора для эксперимента.
- MLflow – параметры, метрики и модели экспериментов, связь с кодом и данными.
- GitHub Actions – автоматические проверки до слияния изменений.
- Мониторинг – время ответа, ошибки и распределения входных данных. Для измерения качества прогнозов нужны реальные цены. Сдвиг данных сам по себе не доказывает ухудшение качества.
- API – проверка обязательных полей и допустимых значений, согласованные коды и формат ошибок. Форма – постоянные подписи.
- Haystack и Ollama – чат. Его назначение и связь с сервисом оценки пока не определены.

Открытые вопросы:

- Какой источник данных доступен и насколько полно он содержит нужные характеристики?
- Для какого города, сегмента жилья и периода должна работать оценка?
- Какая ошибка в рублях и процентах приемлема пользователю? Какие группы квартир особенно важны?
- Доступны ли идентификаторы объектов и даты объявлений для устранения повторов и разделения выборки?
- Откуда получать фактические цены для контроля качества после запуска и как часто обновлять модель?
- Какой дашборд использовать и какие изменения метрик требуют реакции?
- Достаточен ли локальный запуск или нужен внешний деплой? Каковы ожидаемая нагрузка и требования к задержке?
- Какую задачу решает чат и какие документы доступны для его ответов?
