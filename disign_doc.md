
# Дизайн-документ: Сервис прогнозирования цен на жилье (учебный проект MLOps)

## 1. Обзор и постановка проблемы

### 1.1. Что мы строим и зачем
В рамках дисциплины MLOps создается сквозной сервис машинного обучения для прогнозирования рыночной стоимости объектов жилой недвижимости. Сервис принимает на вход базовые характеристики квартиры (площадь, количество комнат, этаж, этажность дома) и возвращает предсказанную цену.

**Бизнес-цель (учебная):** Отработать полный цикл MLOps-зрелости: от анализа данных и трекинга экспериментов до контейнеризации, мониторинга и CI/CD. Реальная бизнес-ценность в данном случае вторична по отношению к демонстрации инженерных практик.

### 1.2. Почему это важно сейчас
Проект является базой для выполнения семинарских заданий. Без работающего дизайн-документа невозможно осмысленно внедрять DVC, MLflow и мониторинг, так как непонятно, какие артефакты и метрики отслеживать.

## 2. Цели и границы проекта

### 2.1. Цели (In-Scope)
1.  Реализовать REST API на Flask для инференса модели.
2.  Обеспечить возможность переключения между моделями (baseline и улучшенная) через переменные окружения или аргументы запуска.
3.  Настроить воспроизводимость данных (DVC) и экспериментов (MLflow).
4.  Развернуть базовый мониторинг (дашборд) и CI/CD пайплайн.

### 2.2. Не-цели (Out-of-Scope)
1.  **Высокая точность предсказания:** Мы не стремимся побить рекорд на Kaggle. Модель нужна как «заглушка» для демонстрации инфраструктуры.
2.  **Сложный парсинг и Feature Engineering:** Входные признаки жестко заданы (4 числовых признака). Использование текстовых описаний или изображений не предусмотрено.
3.  **Продакшен-нагрузка:** Сервис не рассчитан на высокий RPS, не требуется отказоустойчивость уровня 99.99%.

## 3. Данные и метрики

### 3.1. Данные
Используется табличный датасет с характеристиками жилья.
**Признаки:**
*   `area`: Площадь (вещественное число).
*   `rooms`: Количество комнат (целое).
*   `floor`: Этаж квартиры (целое).
*   `total_floors`: Этажность дома (целое).
**Целевая переменная:** `price` (вещественное число).

**Риски данных (Data Leakage):** При разделении выборки необходимо следить, чтобы объекты из одного дома (одинаковый `total_floors` и адрес, если появится) не попадали одновременно в train и test, иначе метрики будут завышены.

### 3.2. Метрики качества модели
*   **Основная метрика:** **MAE (Mean Absolute Error)**. Почему: Для бизнеса (покупателя/продавца) важна абсолютная ошибка в рублях, а не относительная. MAE интерпретируется легче, чем RMSE.
*   **Дополнительная метрика:** **MAPE** (для понимания процента отклонения).
*   **Baseline:** `baseline_const` (константное предсказание медианной цены). Любая ML-модель обязана побить этот baseline на отложенной выборке, иначе ее внедрение не имеет смысла.

## 4. Архитектура и инфраструктура

### 4.1. Высокоуровневая схема
**Компоненты:**
1.  **Клиент:** Веб-браузер или `curl` (отправляет JSON с признаками).
2.  **Сервис (Flask):** Принимает запрос, валидирует входные данные, вызывает функцию из `service/predict.py`, возвращает JSON с ценой.
3.  **Слой моделей:** Словарь `MODELS` в `predict.py`, позволяющий выбирать модель без изменения кода приложения.
4.  **Хранилище артефактов:** Локальная файловая система (в рамках учебного курса) + DVC для версионирования.

### 4.2. Инференс
*   **Endpoints:**
    *   `GET /`: Веб-интерфейс (форма ввода).
    *   `POST /api/numbers`: JSON API для программного вызова.
*   **Формат ответа:** `{"predicted_price": <float>}`.

## 5. Экспериментирование и валидация

### 5.1. Трекинг (MLflow)
Каждый запуск обучения логирует:
*   Параметры модели (гиперпараметры).
*   Метрики (MAE, MAPE на train/val).
*   Артефакт модели (сериализованный файл).
*   Хэш коммита и версию данных (DVC hash).

### 5.2. Схема валидации
Используется **K-Fold Cross-Validation** (K=5) на train-части и отдельный **Holdout set** (20%) для финальной проверки перед регистрацией модели в реестре.

## 6. Внедрение и мониторинг

### 6.1. CI/CD (GitHub Actions)
При пуше в ветку `main`:
1.  Запуск линтера (`flake8`).
2.  Запуск юнит-тестов (проверка, что API возвращает 200 и число).
3.  Сборка Docker-образа (опционально, если требуется в семинаре).

### 6.2. Мониторинг (Дашборд)
Поскольку сервис учебный, мониторим **технические метрики** и **дрифт данных**:
*   **Latency (p95):** Время ответа API.
*   **Error Rate:** Доля 5xx ошибок.
*   **Data Drift:** Сравнение распределения входных признаков (площадь, комнаты) с тренировочным датасетом. Если средняя площадь в запросах резко падает или растет, это сигнал, что модель работает не в тех условиях.

## 7. Риски и компромиссы

| Риск | Вероятность | Митигация |
| :--- | :--- | :--- |
| **Отсутствие данных для LLM части** | Высокая | Для семинара по Haystack + Ollama используем синтетические или публичные текстовые данные, не связанные с ценами на жилье, так как основной пайплайн табличный. |
| **Студенческий код нестабилен** | Средняя | Покрыть критические пути (`predict.py`) простыми тестами. В случае падения модели сервис должен возвращать ошибку 503, а не падать с 500. |
| **Утечка данных при разбиении** | Низкая (данные простые) | Использовать `train_test_split` со стратификацией по количеству комнат или цене (биннинг). |
